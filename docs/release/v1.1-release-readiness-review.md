# Trail v1.1 Release Readiness Review

ENG-106 is the final frozen Trail v1.1 release-readiness review.

This document records the repository-side release gate contract and the external owner actions required before a private-beta release can be considered active.

## Release scope

Trail v1.1 is the private-beta release of the AI-powered engineering memory product defined by the frozen v1.1 architecture and milestones.

The release includes:

- Identity and extension authentication.
- Trusted browser capture with consent, pause, exclusion, sanitation, queueing, synchronization, backend validation, persistence, and retention.
- Problem Session lifecycle, artifacts, solve flow, and deletion.
- Deterministic detection.
- AI enrichment through provider abstractions, redaction, provenance, and background jobs.
- Embeddings, lexical/vector/hybrid retrieval, recommendations, Recall, Ghost Replay, and Timeline surfaces.
- Observability, runbooks, deployment contracts, release package validation, and regression gates.

## P0 blocker policy

A v1.1 release must not proceed with an open P0 repository blocker.

P0 blockers include:

- Failing Maven, pnpm, extension, OpenAPI, migration, Testcontainers, Web Store package, or Docker image validation.
- Known authentication bypass or cross-user data access.
- Known capture without consent.
- Known deletion failure for user-owned data.
- Known secret exposure in source, package, image config, logs, or release artifacts.
- Known unvalidated AI/provider output becoming authoritative user content.
- Known inability to start the backend or apply migrations from a clean PostgreSQL 17/pgvector database.

## Signed release gates

The following gates must be signed by the named release owner before private-beta activation.

This repository provides the gate checklist and validation evidence. External signatures are maintained in the private release checklist and are not committed to the repository.

| Gate | Required evidence | Repository evidence | Required signer |
|---|---|---|---|
| Security | Authentication, authorization, privacy, injection, package, and secret checks pass. | Security/privacy docs, threat model, tests, secret scan, Web Store validator. | Security owner |
| Performance | Startup, heap, search, retention, background jobs, and query-plan fixtures pass. | Performance fixtures and Maven/Testcontainers validation. | Platform owner |
| UX | Accessibility, visual states, consent, Recall, Ghost Replay, Timeline, and no-focus-theft checks pass. | Experience spec and accessibility/visual-state audit. | Product owner |
| Restore | Backup/restore, rollback, migration compatibility, RPO/RTO evidence reviewed. | Render backup/restore/rollback contract; live exercise requires Render access. | Platform owner |
| Disclosure | Chrome Web Store permission/network/privacy disclosures match built package. | Disclosure doc, manifest validation, Web Store package validator. | Release owner |

## Repository readiness decision

The repository is locally release-ready only when:

- The ENG-104 critical regression suite passes.
- Full Maven verification passes.
- Full pnpm verification passes.
- Extension lint, typecheck, tests, and manifest validation pass.
- OpenAPI client check passes.
- Web Store package generation and validation pass.
- Backend Docker image builds.
- No locally fixable P0 blocker remains after the final audit.

## External activation requirements

The release is not externally active until the owner completes:

- Render staging deployment verification.
- Brevo production account/sender readiness, public verification/reset destinations, and domain-authentication follow-up for SPF/DKIM/DMARC before production-scale rollout. Local live Brevo identity-email delivery has been manually verified.
- Live Render backup/restore exercise with measured RPO and RTO.
- Live image rollback exercise.
- Private-beta cohort roster activation.
- Private-beta support channel activation.
- Private-beta security contact publication.
- Chrome Web Store submission or private/staged rollout.
- Gate signatures in the private release checklist.
- 72-hour monitoring plan activation.

## 72-hour monitoring plan

The 72-hour monitoring plan begins immediately after private-beta activation.

### Owners

| Role | Responsibility |
|---|---|
| Release owner | Owns release go/no-go, rollback, cohort communication, and final completion note. |
| Platform owner | Watches backend health, readiness, liveness, database, Flyway, resource usage, and rollback signals. |
| Security owner | Watches auth failures, suspicious capture behavior, privacy reports, injection reports, and support escalations. |
| Support owner | Watches participant reports and confirms content-hidden handling. |
| Product owner | Watches UX-critical reports for consent, Recall, Ghost Replay, Timeline, and deletion. |

### Signals

Monitor for:

- Backend readiness/liveness failures.
- Elevated 5xx responses.
- Authentication and refresh failures.
- Capture ingestion rejection spikes.
- Background job terminal failures.
- AI/provider outage or invalid structured output spikes.
- Search/recommendation failures.
- Deletion failures.
- User reports of capture without consent, missing revoke, cross-user data exposure, hidden content collection, focus theft, or misleading AI certainty.

### Cadence

- Hour 0: verify rollout, health, support channel, security contact, and rollback owner availability.
- Hours 1 through 6: review signals at least hourly.
- Hours 6 through 24: review signals every 3 hours.
- Hours 24 through 72: review signals every 6 hours.
- Hour 72: record final monitoring outcome and open follow-up issues for unresolved non-blockers.

### Rollback triggers

Rollback or halt rollout immediately for:

- Confirmed cross-user data exposure.
- Confirmed capture without consent.
- Confirmed deletion failure.
- Confirmed secret exposure.
- Backend readiness instability that affects active users.
- Chrome package mismatch, unexpected permissions, source maps, remote code, or secrets.
- AI output overriding user-authored final solutions.

## Deferred

ENG-106 does not create new product capabilities, change architecture, add telemetry, deploy Render without credentials, submit to Chrome Web Store without account access, fabricate external signatures, or claim external signatures were completed.

It does not claim external signatures exist until the owner records them in the private release checklist.
